# Sidebar stage-2 protocol (#865, PR 3)

The [proposal, Claude review and maintainer decisions of 2026-10-13](https://github.com/tkakkie/ribbitto/issues/865) fix this protocol before measurement. **Runs start only on the maintainer's explicit instruction**, after harness review and functional checks. The current slices add the contract and operation measurement primitives; there is no runner yet. 36/26 remains a validation configuration; activation is a separate decision, and #832/#865 remain open.

The driver will extend `cmd/loadgen`: its [HTTP-only boundary](packages.md) and [existing transport, complete-frame parser and receipt comparison](load-client.md) support the real authenticated workload without application imports. Stage 2 pins a loopback HTTP target for HTTP/1.1; the existing HTTPS transport negotiates HTTP/2 and must not be used. The old stability evaluator is private `realtime_test` code, not importable; this slice records the [unchanged rule](stream-sidebar-stability.md), without duplicating its evaluator. Extraction/reuse belongs to the evaluator slice.

Each fresh fixture has one organisation, four channels, one hot channel with two named topics, 500 seeded messages/channel, and N distinct members/streams. Posts, reads and pages split 50:50 feed/topic. Independent schedules run for 600 s after establishment/initial snapshots, then drain separately for 30 s. Only stability trends exclude the first 60 s. Churn waits 250 ms plus seeded 0–250 ms jitter, retains complete durable cursors, and never waits for capacity. POSTs have one attempt. Three paired rounds alternate sync/async, async/sync, sync/async; identical seeds within each pair give 24 windows. Sync sets URL pool_max_conns=36; async C/W/M/R/E/P/H=36/26/100/3/20/2/10. Async needs 3/3 in every group; keep every failure and report median/min–max.

Every async feed/topic endpoint separately needs post/read p50/p95/p99 ≤50/150/300 ms, page ≤100/300/600 ms, and each percentile ≤paired sync plus max(20% of sync, 10 ms). Dispatch through complete response body is the HTTP clock; all scheduled work must succeed. Establishment/normal work allow zero 503s. At most 0.1% of logical replacements may encounter 503, each recovering within 2 s; retries never enlarge that denominator. Unexpected 429s, failures, resets, live errors, closed admission or unexplained cancellations fail.

Async headroom gates: acquired p95/p99/max ≤32/35/36; at C in ≤1% of samples and never three consecutively; empty/acquire deltas ≤1%; mean empty wait ≤5 ms (zero without empty acquisitions); waiting pressure ≤0.1 caller for the whole window and every planned 60 s bucket. Preserve full per-second telemetry, counts and durations, refusal reconciliation, cancellation attribution and the stability completeness/spike rules. Sampled maxima are not exact peaks. Message receipt after POST response p95 ≤250 ms; witnessed sidebar freshness after posts and reads separately p95/p99 ≤2/5 s. Keep early/negative receipts, scheduled-to-receipt percentiles, offline replay separately, and complete final snapshots/replay. The same-snapshot event/read-state witness is disposable-only, off by default and reviewed separately. Functional prerequisites remain in both arms. Quiet-host/MEASURING rules follow [stage 1](stream-sidebar-stage1.md).

`cmd/loadgen/stage2.go` defines version-1 window and manifest JSON contracts: field names retain Go's case; durations carry NS/MS/Seconds suffixes; limits carry units and percentile order. Every field is required, even zero; arrays use `[]`, not null. Response-relative message/post/read receipt summaries retain `Early` (strictly negative count) and signed `MinMS`, including zero for no observations; counts and minimum signs must agree. Every latency summary requires p50 ≤ p95 ≤ p99 and all-zero values when its count is zero; non-receipt latency summaries must be nonnegative, and signed receipts require MinMS ≤ p50. Decoding rejects missing/null/extra/duplicate record fields, unknown versions and altered protocols. Metrics retain all six server sections verbatim (section contents follow [development metrics](dev-metrics.md)). Both windows and manifests require exactly one verdict per pinned protocol gate ID; missing (including empty lists), duplicate and unknown IDs are rejected. Verdict states are `pass`, `reject` and `inconclusive`. A gate that cannot be evaluated, including a non-applicable gate (such as an async-only gate in a sync window) or a paired gate awaiting its counterpart, takes `inconclusive`; it is never omitted or treated as a pass.

Each pinned gate has `Arms`, the window arms in which its verdict may be evaluated; decoding uses this field, not the descriptive `Scope`. Normal-work absolute latency, headroom and stability gates use `["async"]`; `normal-503`, `replacement-503`, delivery/freshness and `complete` use `["sync","async"]`. Paired gates need both arms' evidence but record their verdict only in the async window against its paired sync result (`Arms: ["async"]`): sync windows always record them as `inconclusive`, as do async windows awaiting the sync result (including round 2). A window rejects `pass` or `reject` for any gate whose `Arms` excludes its configured arm; both-arm gates accept all three states in either arm. Manifest verdicts aggregate the full run across applicable windows/pairs, so every gate accepts all three states without a window-arm restriction; evidence sufficiency and aggregation belong to the evaluator slice. Adding `Arms` changes the pinned protocol and window/manifest example hashes within this pre-measurement version-1 contract.

Windows carry seeds/configuration, effective startup/metrics evidence, samples, operation clocks/counts, all attempts, refusal totals, delivery/freshness and gate IDs/states/measured values. Manifests carry host conditions and exactly one entry per planned group/arm/round (24, independent of seeds). Each entry has `State` and `Reason`: `completed` requires file/SHA256/effective evidence and an empty reason; `failed` requires a reason, retains any effective evidence and optionally a valid file/hash pair; `unrun` requires a reason, empty file/hash and null effective evidence. These are execution states; gate verdicts report measurement failures. Schema validity does not certify passing measurements; later slices implement evaluators, witnesses, drivers and archive reconciliation. No initial connection comparison: only evidence of pressure triggers 36/26 versus 38/26.

Slice 2-1 adds independent, seeded fixed-rate slots for posts, reads, pages and replacements, alternating feed/topic with exact 50:50 totals. Polling never waits for admission: expired slots (including at window end) and capacity misses are retained. HTTP exchanges have one attempt and a 10 s deadline, measure dispatch through complete-body consumption before closing, and retain body/close errors and timeouts. At most 1 MiB is retained for proof; excess bytes are fully drained and exceeding the cap alone does not fail an operation. Feed posts and reads use `HX-Request: true`: success is 200 for feed posts, 303 for topic posts, 204 for reads, and 200 for page GETs/SSE connects. A read returning 200 fails without invoking verification. Read classification requires caller-supplied proof of persisted advancement, independent of the empty 204 response; a successful no-op is counted separately and cannot satisfy offered changed reads. The fixture, proof provider and SSE replacement driver are later slices.

Summaries use exact nearest-rank p50/p95/p99. HTTP and dispatch lateness include every executed logical operation, including failures, timeouts, no-ops and unverified reads; missed slots never executed and have neither sample. Scheduled-to-response includes every scheduled slot, using elapsed scheduled-to-detection time for misses. Misses remain in `Scheduled` and `Missed`; the completeness gate must reject any miss. `Failed` includes timeouts, unverified reads and no-ops; `Missed` is separate. All slots must be polled and admitted work settled before summarizing; replacement attempt records accept actual dispatch/offline timestamps without implementing SSE or retry policy.

Slice 2-2 evaluates absolute and paired HTTP gates per operation/endpoint, requiring every scheduled operation to succeed (reads must advance); empty absolute evidence rejects. Window evidence must contain exactly one summary for each post/read/page/replacement × feed/topic pair, in any order; duplicates, unknown pairs and missing pairs are invalid. Decoding rejects invalid window evidence. Evaluation returns an error before changing refusal counts or gate verdicts if either the window or a supplied paired window has invalid operations; callers must treat that error as unusable evidence. Paired evidence must match group, round and both seeds and come from the sync arm; until available, paired verdicts are inconclusive. Refusal accounting groups replacement attempts by globally numbered logical ID, counts scheduled replacements including misses, and counts retries separately. `Refused503`, `Attempts` and `Retries` in `Refusals` cover replacements only; the shared summary collects all attempts, including establishment without an operation summary, for `normal-503`'s measured count. Recovery uses the first successful reconnect by attempt number, regardless of collection order, with its offline-to-response outage for each affected replacement. A replacement attempt without an offline timestamp records `OutageNS = -1` as missing evidence; measured zero remains valid. An unrecovered affected replacement or a first reconnect with missing outage evidence rejects; later successes cannot repair it. Inclusive limits permit exactly 0.1% and 2 s. Other gates remain inconclusive placeholders; the JSON fields are unchanged.
