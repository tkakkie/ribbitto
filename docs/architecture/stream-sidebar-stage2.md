# Sidebar stage-2 protocol (#865, PR 3)

The [proposal, Claude review and maintainer decisions of 2026-10-13](https://github.com/tkakkie/ribbitto/issues/865) fix this protocol before measurement. **Runs start only on the maintainer's explicit instruction**, after harness review and functional checks. This slice adds a contract, not a runner. 36/26 remains a validation configuration; activation is a separate decision, and #832/#865 remain open.

The driver will extend `cmd/loadgen`: its [HTTP-only boundary](packages.md) and [existing transport, complete-frame parser and receipt comparison](load-client.md) support the real authenticated workload without application imports. Stage 2 pins a loopback HTTP target for HTTP/1.1; the existing HTTPS transport negotiates HTTP/2 and must not be used. The old stability evaluator is private `realtime_test` code, not importable; this slice records the [unchanged rule](stream-sidebar-stability.md), without duplicating its evaluator. Extraction/reuse belongs to the evaluator slice.

Each fresh fixture has one organisation, four channels, one hot channel with two named topics, 500 seeded messages/channel, and N distinct members/streams. Posts, reads and pages split 50:50 feed/topic. Independent schedules run for 600 s after establishment/initial snapshots, then drain separately for 30 s. Only stability trends exclude the first 60 s. Churn waits 250 ms plus seeded 0–250 ms jitter, retains complete durable cursors, and never waits for capacity. POSTs have one attempt. Three paired rounds alternate sync/async, async/sync, sync/async; identical seeds within each pair give 24 windows. Sync sets URL pool_max_conns=36; async C/W/M/R/E/P/H=36/26/100/3/20/2/10. Async needs 3/3 in every group; keep every failure and report median/min–max.

Every async feed/topic endpoint separately needs post/read p50/p95/p99 ≤50/150/300 ms, page ≤100/300/600 ms, and each percentile ≤paired sync plus max(20% of sync, 10 ms). Dispatch through complete response body is the HTTP clock; all scheduled work must succeed. Establishment/normal work allow zero 503s. At most 0.1% of logical replacements may encounter 503, each recovering within 2 s; retries never enlarge that denominator. Unexpected 429s, failures, resets, live errors, closed admission or unexplained cancellations fail.

Async headroom gates: acquired p95/p99/max ≤32/35/36; at C in ≤1% of samples and never three consecutively; empty/acquire deltas ≤1%; mean empty wait ≤5 ms (zero without empty acquisitions); waiting pressure ≤0.1 caller for the whole window and every planned 60 s bucket. Preserve full per-second telemetry, counts and durations, refusal reconciliation, cancellation attribution and the stability completeness/spike rules. Sampled maxima are not exact peaks. Message receipt after POST response p95 ≤250 ms; witnessed sidebar freshness after posts and reads separately p95/p99 ≤2/5 s. Keep early/negative receipts, scheduled-to-receipt percentiles, offline replay separately, and complete final snapshots/replay. The same-snapshot event/read-state witness is disposable-only, off by default and reviewed separately. Functional prerequisites remain in both arms. Quiet-host/MEASURING rules follow [stage 1](stream-sidebar-stage1.md).

`cmd/loadgen/stage2.go` defines version-1 window and manifest JSON contracts: field names retain Go's case; durations carry NS/MS/Seconds suffixes; limits carry units and percentile order. Every field is required, even zero; arrays use `[]`, not null. Response-relative message/post/read receipt summaries retain `Early` (strictly negative count) and signed `MinMS`, including zero for no observations; counts and minimum signs must agree. Decoding rejects missing/null/extra/duplicate record fields, unknown versions and altered protocols. Metrics retain all six server sections verbatim (section contents follow [development metrics](dev-metrics.md)). Windows carry seeds/configuration, effective startup/metrics evidence, samples, operation clocks/counts, all attempts, refusal totals, delivery/freshness and gate IDs/states/measured values. Manifests carry host conditions and exactly one entry per planned group/arm/round (24, independent of seeds). Each entry has `State` and `Reason`: `completed` requires file/SHA256/effective evidence and an empty reason; `failed` requires a reason, retains any effective evidence and optionally a valid file/hash pair; `unrun` requires a reason, empty file/hash and null effective evidence. These are execution states; gate verdicts report measurement failures. Schema validity does not certify passing measurements; later slices implement evaluators, witnesses, scheduling and archive reconciliation. No initial connection comparison: only evidence of pressure triggers 36/26 versus 38/26.
